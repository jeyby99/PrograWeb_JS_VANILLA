## Objectives

### General objective
Build a full-stack web application that connects a Spring Boot REST backend to a JavaScript frontend, and consumes one external public API (Rick and Morty API) by combining and chaining several of its endpoints.

### Specific objectives
- Implement a complete **CRUD** (Create, Read, Update, Delete) with Spring Boot and PostgreSQL.
- Expose a **REST API** with search by name.
- Build a **real-time search** page connected to our own backend (Page 1).
- Build a search page with a **4-second debounce** that **combines 3 endpoints** of the Rick and Morty API using **chained requests** with **jQuery** (Page 2).
- **Validate** the user input before sending a request, and validate the API response before showing it.
- Make the interface **responsive** using Bootstrap, Tailwind, CSS Grid, Flexbox and Media Queries.
- **Verify** that Page 2 works using automated end-to-end tests with **Playwright**.

## Scope

**Included**
- CRUD of entities (first name, last name, email) with Thymeleaf views.
- REST API at `/api/entidades` with CORS enabled.
- Page 1: real-time search against the project's own backend.
- Page 2: debounced search against the Rick and Morty API (`character`, `location`, `episode`), with input validation, chained requests and error handling.
- Responsive design for mobile, tablet and desktop.
- Playwright end-to-end tests for Page 2.

**Not included**
- User authentication or authorization.
- Automated tests for the Java backend and for Page 1.
- Deployment to a production server (the app runs locally).

## Architecture

The project follows a **client-server architecture** with a **layered architecture** on the backend:

```
┌──────────────────────┐        HTTP / JSON        ┌───────────────────────────────┐
│  Frontend (jQuery)   │ ────────────────────────► │  Spring Boot Backend          │
│  pagina1.html        │                           │                               │
│  pagina2.html        │                           │  Controller  (REST + MVC)     │
└──────────┬───────────┘                           │      │                        │
           │                                       │  Service     (business logic) │
           │ $.ajax (Page 2 only)                  │      │                        │
           ▼                                       │  Repository  (Spring Data JPA)│
┌──────────────────────┐                           │      │                        │
│  Rick and Morty API  │                           │  Model       (JPA Entity)     │
│  /character          │                           └──────┼────────────────────────┘
│  /location           │                                  ▼
│  /episode            │                           ┌──────────────┐
└──────────────────────┘                           │  PostgreSQL  │
                                                   └──────────────┘
```

- **Controller layer:** receives HTTP requests (MVC controller for Thymeleaf views and REST controller for JSON).
- **Service layer:** contains the business logic.
- **Repository layer:** database access through Spring Data JPA.
- **Model layer:** JPA entity mapped to a PostgreSQL table.
- **Page 1** talks to our own REST API. **Page 2** talks directly to the Rick and Morty API from the browser.

### Page 2: chained requests

```
User types ──► validate input ──► wait 4 s (debounce) ──► runSearch(query)
                                                              │
   1) GET /character/?name=query ─────────────────────────────┤  (first request)
                      │ response: characters (max 6)          │
                      ▼ ids taken from the response          │
   2) GET /location/{ids}   ┐  in parallel ($.when)           │  (second wave:
   3) GET /episode/{ids}    ┘                                 │   depends on 1)
                      │                                       │
                      ▼                                       │
   Combine the 3 responses ──► one card per character (image, name, species/status,
                               location, dimension, first episode)
```

## Design Pattern

**Main pattern: MVC (Model-View-Controller)**, complemented by the **Repository pattern** and **Dependency Injection**.

**Why MVC?**
- It separates data (Model), presentation (Thymeleaf views and HTML pages) and request handling (Controllers), so each part can change without breaking the others.
- It is the natural pattern of Spring Boot web applications, which keeps the code organized and easy to maintain.

**Why the Repository pattern?**
- `EntidadRepository` hides the database access details. The rest of the application works with Java objects and never writes SQL directly.

**Why Dependency Injection?**
- Spring injects the services and repositories where they are needed, which reduces coupling between classes.

## Programming Paradigm

**Backend: Object-Oriented Programming (OOP).**
- Java is an object-oriented language, and the project models its domain with classes (`Entidad`), encapsulation (private attributes with getters and setters) and separation of responsibilities between classes.
- OOP fits Spring and JPA, where entities are objects mapped to database tables.

**Frontend: Event-driven and asynchronous programming.**
- The pages react to user events (typing, Enter key, button click).
- jQuery's `$.ajax` returns promises (Deferred objects). Page 2 chains them with `.then()` (the second wave of requests needs data from the first response) and runs independent requests in parallel with `$.when()`.
- If one of the secondary requests fails, the page still shows the characters and warns the user.
- Array methods such as `map`, `filter` and `slice` add a functional style when transforming the results.

## Features

### Backend
- Complete CRUD of entities (first name, last name, email) with Thymeleaf views.
- REST API at `/api/entidades` with search by name (`?query=`) and CORS enabled.

### Page 1 – Real-time search
Queries the project's backend on every keystroke and displays the records as cards.

### Page 2 – Rick and Morty search
- **Debounce:** waits 4 seconds after the user stops typing (or Enter / Search button to search immediately). A countdown is shown on screen.
- **3 combined endpoints, chained:**

| Step | Endpoint | Used for |
|---|---|---|
| 1 | `GET /character/?name=...` | Finds the characters (name, species, status, image) |
| 2 | `GET /location/{ids}` | Location name, type and dimension (ids come from step 1) |
| 3 | `GET /episode/{ids}` | First episode code and name (ids come from step 1) |

- **Request validation (before sending):** 2 to 30 characters; only letters, numbers, spaces, dot, apostrophe and hyphen; extra spaces are cleaned; the value is URL-encoded. Invalid input shows a message and no request is sent.
- **Response validation:** checks that `results` is an array and that each item has an `id` and a `name`; images are accepted only from the API's own host; text is inserted with `.text()` so no HTML from the API is executed.
- **Error handling:** no results (404), server error, timeout, no connection and partial failure each show their own message. Old responses are ignored when a newer search was made.
- **Responsive:** CSS Grid with 3 columns (desktop), 2 (tablet) and 1 (mobile) using Media Queries; Flexbox for the search bar and the cards; Bootstrap and Tailwind utility classes.
- On load, the page shows "Rick" characters by default.

## Testing with Playwright

The tests are in `e2e/pagina2.spec.js` and check Page 2:

- It loads 6 cards with image and description, and uses jQuery (`$.ajax` / XHR).
- The 3 endpoints are called and **chained** (`/character` first, then `/location` and `/episode` with ids from the first response).
- **Debounce:** no request before 4 s, one request at 4 s, and typing again restarts the wait.
- Enter and the Search button search immediately.
- **Input validation:** invalid values (too short, too long, `<script>`, SQL-like text, `../`) send no request.
- **Response handling:** no results, HTTP 500, no connection, partial failure (`/episode` or `/location` down), old responses ignored, and HTML in API data is not executed.
- **Responsive:** 3, 2 and 1 columns at 1280, 820 and 375 px, with no horizontal scroll.
- `@live`: one optional test that calls the real API.

Normal tests use **simulated API responses** (mock data), so they are fast and do not need internet. The `@live` test uses the real API.

```bash
npm install                 # first time only
npx playwright install chromium   # first time only: downloads the browser
npm test                    # runs the tests (starts its own static server on port 4173)
npm run report              # opens the HTML report
npm run test:live           # optional: also tests against the real API
```

To test the page served by your Spring Boot app instead (start the app first):

```bash
# Windows cmd
set BASE_URL=http://localhost:8080 && npm test
# Windows PowerShell
$env:BASE_URL="http://localhost:8080"; npm test
```

## How to Run

**Requirements:** JDK 25, Maven and PostgreSQL. Node.js 18+ only if you want to run the tests.

1. Create the database in PostgreSQL:
   ```sql
   CREATE DATABASE "PrograWeb";
   ```
2. Set your username and password in `src/main/resources/application.properties`:
   ```properties
   spring.datasource.url=jdbc:postgresql://localhost:5432/PrograWeb
   spring.datasource.username=postgres
   spring.datasource.password=YOUR_PASSWORD
   ```
3. Run the application:
   ```bash
   mvn spring-boot:run
   ```
4. Open in the browser:
   - Home and CRUD: http://localhost:8080
   - Page 1: http://localhost:8080/pagina1.html
   - Page 2: http://localhost:8080/pagina2.html

Tables are created automatically thanks to `spring.jpa.hibernate.ddl-auto=update`.
