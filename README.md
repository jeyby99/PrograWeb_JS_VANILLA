## Objectives

### General objective
Build a full-stack web application that connects a Spring Boot REST backend to a JavaScript frontend, and consumes one external public API (Rick and Morty API) by combining and chaining several of its endpoints.

### Specific objectives
- Implement a complete **CRUD** (Create, Read, Update, Delete) with Spring Boot and PostgreSQL.
- Expose a **REST API** with search by name.
- Build a **real-time search** page connected to our own backend (Page 1).
- Build a search page with a **4-second debounce** that **combines 3 endpoints** of the Rick and Morty API using **chained requests** with **jQuery** (Page 2).
- **Validate** the user input before sending a request, and validate the API response before showing it.
- Make the interface **responsive** using Bootstrap, Tailwind, CSS Grid, Flexbox and Media Queries.
- **Verify** that Page 2 works using automated end-to-end tests with **Playwright**.

## Scope

**Included**
- CRUD of entities (first name, last name, email) with Thymeleaf views.
- REST API at `/api/entidades` with CORS enabled.
- Page 1: real-time search against the project's own backend.
- Page 2: debounced search against the Rick and Morty API (`character`, `location`, `episode`), with input validation, chained requests and error handling.
- Responsive design for mobile, tablet and desktop.
- Playwright end-to-end tests for Page 2.

**Not included**
- User authentication or authorization.
- Automated tests for the Java backend and for Page 1.
- Deployment to a production server (the app runs locally or with Docker; the image is published to GHCR).

## Architecture

The project follows a **client-server architecture** with a **layered architecture** on the backend. Since SCRUM-23 every request enters through an **API Gateway** (see [API Gateway](#api-gateway)); the diagram below shows the backend layers behind it:

```
┌──────────────────────┐        HTTP / JSON        ┌───────────────────────────────┐
│  Frontend (jQuery)   │ ────────────────────────► │  Spring Boot Backend          │
│  pagina1.html        │                           │                               │
│  pagina2.html        │                           │  Controller  (REST + MVC)     │
└──────────┬───────────┘                           │      │                        │
           │                                       │  Service     (business logic) │
           │ $.ajax (Page 2 only)                  │      │                        │
           ▼                                       │  Repository  (Spring Data JPA)│
┌──────────────────────┐                           │      │                        │
│  Rick and Morty API  │                           │  Model       (JPA Entity)     │
│  /character          │                           └──────┼────────────────────────┘
│  /location           │                                  ▼
│  /episode            │                           ┌──────────────┐
└──────────────────────┘                           │  PostgreSQL  │
                                                   └──────────────┘
```

- **Controller layer:** receives HTTP requests (MVC controller for Thymeleaf views and REST controller for JSON).
- **Service layer:** contains the business logic.
- **Repository layer:** database access through Spring Data JPA.
- **Model layer:** JPA entity mapped to a PostgreSQL table.
- **Page 1** talks to our own REST API. **Page 2** talks directly to the Rick and Morty API from the browser.

### API Gateway

**What:** a separate Spring Boot service (`gateway/`, Spring Cloud Gateway) that is the **single entry point** of the application, on port **8080**. The three backend instances also answer directly on **8081, 8082 and 8083** (required for the load-balancing demo); on AWS only 8080 is open to the internet by default.

```
                                                          ┌──► app1 :8081 ──┐
Browser ──:8080──► API Gateway ──(/api/**, /, pages)── LB ─┼──► app2 :8082 ──┼──► PostgreSQL
                        │                                  └──► app3 :8083 ──┘
                        └──(/rickandmorty/**)──► https://rickandmortyapi.com/api/**

Every request gets an X-Request-Id and one log line (method, path, status, time).
```

**Routes** (`gateway/src/main/resources/application.yml`):

| Route id | Path | Destination | Filters |
|---|---|---|---|
| `backend-api` | `/api/**` | `lb://prograweb-backend` (app1, app2, app3) | `PreserveHostHeader`, `Retry` (GET) |
| `rick-and-morty` | `/rickandmorty/**` | `https://rickandmortyapi.com/api/**` | `RewritePath` |
| `backend-web` | everything else (order 1000, last) | `lb://prograweb-backend` (app1, app2, app3) | `PreserveHostHeader`, `Retry` (GET) |

**Cross-cutting concerns handled in one place:**
- `RequestLoggingFilter` (global filter): assigns an `X-Request-Id` (keeps a valid one sent by the client), forwards it to the backend, returns it in the response and logs `GET /api/entidades -> 200 OK in 20 ms [id]`.
- Default filters: `X-Gateway: prograweb-gateway` on every response; `DedupeResponseHeader` keeps a single CORS header when both gateway and backend send one.
- CORS for `/api/**`, health check at `/actuator/health`.
- `PreserveHostHeader` on backend routes: without it the CRUD form redirects to `http://app:8080/...`, an internal Docker name the browser cannot open.

**Why a gateway:** one public entry point (the backend and database are no longer exposed), one place for logging, tracing and CORS, and the freedom to move or split backend services without changing the clients.

### Load Balancer

**What:** the gateway spreads the backend traffic over **three instances** (`app1` :8081, `app2` :8082, `app3` :8083: same image, same PostgreSQL) with **Spring Cloud LoadBalancer**. Routes use `lb://prograweb-backend` instead of a fixed URL.

| Piece | Configuration | Effect |
|---|---|---|
| Instance list | `spring.cloud.discovery.client.simple.instances.prograweb-backend` = `BACKEND_1_URL`, `BACKEND_2_URL`, `BACKEND_3_URL` | Static list, no service registry needed |
| Algorithm | Round robin (default) | Each instance gets about a third of the requests. The exact order can shift when the health check refreshes the list every 5 s (60 requests: 18 / 21 / 21) |
| Health check | `spring.cloud.loadbalancer.configurations: health-check`, every 5 s on `/api/entidades` | A failing instance leaves the rotation and comes back when it recovers |
| Retry | `Retry` filter, 1 retry, GET only, on 5xx or connection errors | A request that hits a dead instance is retried on the next one, so the user sees no error |
| Timeouts | `httpclient.connect-timeout: 2000`, `response-timeout: 5s` | A backend that does not answer in time becomes a 504 instead of an endless wait |
| `X-Served-By` | `ServedByFilter` in the backend (`INSTANCE_NAME`) | Shows which instance answered |

Each instance starts after the previous one is healthy (`app1` → `app2` → `app3`), so only one creates the tables (`ddl-auto=update`). All share the database, so data written through one instance is read through the others.

**Resource limits** (fixed on purpose so load tests are repeatable and fit an EC2 t3.medium, 2 vCPU / 4 GB): each instance and the gateway have `mem_limit: 512m` and `cpus: 0.5`; the JVM heap is set with `JAVA_TOOL_OPTIONS` (320 MB backend, 256 MB gateway); PostgreSQL `mem_limit: 512m`. SQL logging is off in containers (`SPRING_JPA_SHOW_SQL=false`).

**Why:** with one backend, a crash takes the whole app down. With three behind the balancer the app keeps answering when one fails, and more instances can be added for more load. Only `POST` is not retried: repeating it could create a record twice.

**Good vs bad balancer (demo):** the gateway profile `bad-balancer` (`gateway/src/main/resources/application-bad-balancer.yml`) keeps the same 3 instances, round robin and timeouts, but turns the protections off, to show why they matter. Every response carries `X-Balancer: good` or `X-Balancer: bad`.

| | Good balancer (default) | Bad balancer (`GATEWAY_PROFILE=bad-balancer`) |
|---|---|---|
| Health check | Every 5 s; a dead instance leaves the rotation | Off: a dead instance keeps receiving traffic |
| Retry | GET retried once on the next instance | Off: the client receives the error |
| One instance down | ~0% errors (measured: 12/12 OK) | ~1 of every 3 requests fails with 5xx (measured: 4/12 → 500) |

```bash
# --no-deps: switch only the gateway, without starting a stopped instance again
GATEWAY_PROFILE=bad-balancer docker compose up -d --no-deps gateway   # bad balancer
docker compose up -d --no-deps gateway                                 # back to the good one
```

**Try it:**

```bash
for i in 1 2 3 4 5 6; do curl -s -D - -o /dev/null http://localhost:8080/api/entidades | grep X-Served-By; done
curl -s -D - -o /dev/null http://localhost:8082/api/entidades | grep X-Served-By   # one instance directly
docker compose stop app2      # requests keep answering 200 from app1 and app3
docker compose start app2     # app2 joins the rotation again
```

### Page 2: chained requests

```
User types ──► validate input ──► wait 4 s (debounce) ──► runSearch(query)
                                                              │
   1) GET /character/?name=query ─────────────────────────────┤  (first request)
                      │ response: characters (max 6)          │
                      ▼ ids taken from the response          │
   2) GET /location/{ids}   ┐  in parallel ($.when)           │  (second wave:
   3) GET /episode/{ids}    ┘                                 │   depends on 1)
                      │                                       │
                      ▼                                       │
   Combine the 3 responses ──► one card per character (image, name, species/status,
                               location, dimension, first episode)
```

## Design Pattern

**Main pattern: MVC (Model-View-Controller)**, complemented by the **Repository pattern** and **Dependency Injection**.

**Why MVC?**
- It separates data (Model), presentation (Thymeleaf views and HTML pages) and request handling (Controllers), so each part can change without breaking the others.
- It is the natural pattern of Spring Boot web applications, which keeps the code organized and easy to maintain.

**Why the Repository pattern?**
- `EntidadRepository` hides the database access details. The rest of the application works with Java objects and never writes SQL directly.

**Why Dependency Injection?**
- Spring injects the services and repositories where they are needed, which reduces coupling between classes.

## Programming Paradigm

**Backend: Object-Oriented Programming (OOP).**
- Java is an object-oriented language, and the project models its domain with classes (`Entidad`), encapsulation (private attributes with getters and setters) and separation of responsibilities between classes.
- OOP fits Spring and JPA, where entities are objects mapped to database tables.

**Frontend: Event-driven and asynchronous programming.**
- The pages react to user events (typing, Enter key, button click).
- jQuery's `$.ajax` returns promises (Deferred objects). Page 2 chains them with `.then()` (the second wave of requests needs data from the first response) and runs independent requests in parallel with `$.when()`.
- If one of the secondary requests fails, the page still shows the characters and warns the user.
- Array methods such as `map`, `filter` and `slice` add a functional style when transforming the results.

## Features

### Backend
- Complete CRUD of entities (first name, last name, email) with Thymeleaf views.
- REST API at `/api/entidades` with search by name (`?query=`) and CORS enabled.

### Page 1 – Real-time search
Queries the project's backend on every keystroke and displays the records as cards.

### Page 2 – Rick and Morty search
- **Debounce:** waits 4 seconds after the user stops typing (or Enter / Search button to search immediately). A countdown is shown on screen.
- **3 combined endpoints, chained:**

| Step | Endpoint | Used for |
|---|---|---|
| 1 | `GET /character/?name=...` | Finds the characters (name, species, status, image) |
| 2 | `GET /location/{ids}` | Location name, type and dimension (ids come from step 1) |
| 3 | `GET /episode/{ids}` | First episode code and name (ids come from step 1) |

- **Request validation (before sending):** 2 to 30 characters; only letters, numbers, spaces, dot, apostrophe and hyphen; extra spaces are cleaned; the value is URL-encoded. Invalid input shows a message and no request is sent.
- **Response validation:** checks that `results` is an array and that each item has an `id` and a `name`; images are accepted only from the API's own host; text is inserted with `.text()` so no HTML from the API is executed.
- **Error handling:** no results (404), server error, timeout, no connection and partial failure each show their own message. Old responses are ignored when a newer search was made.
- **Responsive:** CSS Grid with 3 columns (desktop), 2 (tablet) and 1 (mobile) using Media Queries; Flexbox for the search bar and the cards; Bootstrap and Tailwind utility classes.
- **Search by season / episode:** the query is split into a name and an episode code, as supported by `/episode?episode=` (partial codes):

| Input | Episode code | Meaning |
|---|---|---|
| `morty temporada 4`, `morty season 4`, `morty T4` | `S04` | Mortys in season 4 |
| `morty cap 4`, `morty capítulo 4`, `morty episodio 4`, `morty ep 4` | `E04` | Mortys in episode 4 of any season |
| `morty temporada 4 cap 2`, `morty S04E02` | `S04E02` | Mortys in that episode |
| `temporada 4` | `S04` | every character in season 4 |

  With a code, the chain is `/episode?episode=CODE` → `/character/{ids}` (filtered by name) → `/location/{ids}`, and each card shows the matching episode.
- **Pagination:** 6 characters per page with `« Anterior`, page numbers and `Siguiente »`. Name searches map each page to the API's 20-item pages (cached); season/episode searches paginate on the client and only request `/location` per page.
- On load, the page shows "Rick" characters by default.

## Testing with Playwright

The tests are in `e2e/pagina2.spec.js` and check Page 2:

- It loads 6 cards with image and description, and uses jQuery (`$.ajax` / XHR).
- The 3 endpoints are called and **chained** (`/character` first, then `/location` and `/episode` with ids from the first response).
- **Debounce:** no request before 4 s, one request at 4 s, and typing again restarts the wait.
- Enter and the Search button search immediately.
- **Input validation:** invalid values (too short, too long, `<script>`, SQL-like text, `../`) send no request.
- **Response handling:** no results, HTTP 500, no connection, partial failure (`/episode` or `/location` down), old responses ignored, and HTML in API data is not executed.
- **Responsive:** 3, 2 and 1 columns at 1280, 820 and 375 px, with no horizontal scroll.
- **Season / episode search:** request order, character ids taken from the episodes, and the parsing of Spanish/English keywords and codes.
- **Pagination:** next/previous, jumping by page number across API pages, cache, client-side paging for season searches, hidden when not needed.
- `@live`: one optional test that calls the real API.

Normal tests use **simulated API responses** (mock data), so they are fast and do not need internet. The `@live` test uses the real API.

```bash
npm install                 # first time only
npx playwright install chromium   # first time only: downloads the browser
npm test                    # runs the tests (starts its own static server on port 4173)
npm run report              # opens the HTML report
npm run test:live           # optional: also tests against the real API
```

To test the page served by your Spring Boot app instead (start the app first):

```bash
# Windows cmd
set BASE_URL=http://localhost:8080 && npm test
# Windows PowerShell
$env:BASE_URL="http://localhost:8080"; npm test
```

### Load testing with k6

The load balancer is tested with [k6](https://k6.io) (`loadtest/`). k6 runs in Docker, so nothing needs to be installed; reports (HTML dashboard + JSON summary) are written to `loadtest/reports/` (ignored by git).

| Script | Load | What it shows | Pass criteria |
|---|---|---|---|
| `smoke.js` | 1 user, 30 s | Everything answers before heavier tests | 0 errors, p95 < 1 s |
| `load.js` | ramp to 30 users, hold 1 min | Normal expected load | errors < 1%, p95 < 800 ms |
| `stress.js` | 50 → 100 → 200 → 400 → 600 users, no pauses | **Breaking point**: where latency explodes and requests fail. Expected to fail | marks errors > 5% / p95 > 2 s as broken |
| `failover.js` | 20 users, 2 min; one instance stopped at ~0:30 and started at ~1:30 | Good vs bad balancer when an instance dies | errors < 1% |

Every script counts responses per instance (`X-Served-By`) in the `served_by` metric; `instance:none` = error responses that never reached an instance.

```bash
loadtest/run.sh smoke                                    # local docker compose (gateway on :8080)
loadtest/run.sh load
loadtest/run.sh stress
loadtest/failover-demo.sh good                           # local: stops/starts app2 automatically
loadtest/failover-demo.sh bad                            # same with GATEWAY_PROFILE=bad-balancer
BASE_URL=http://<elastic-ip>:8080 loadtest/run.sh load   # against the EC2 test server
```

**Results on a local machine** (Docker Desktop, limits from `docker-compose.yml`):

| Test | Requests | Errors | p95 | Distribution app1 / app2 / app3 | Result |
|---|---|---|---|---|---|
| smoke | 30 | 0% | 41 ms | 10 / 10 / 10 | pass |
| load (30 users) | 3,509 (33/s) | 0% | 406 ms | 1,180 / 1,165 / 1,164 | pass |
| stress (up to 600 users) | 13,668 (76/s) | 3.7% (504 timeouts) | **8.7 s** | 4,307 / 4,579 / 4,278 | **breaks**: p95 4× over the limit |
| failover, good balancer | 6,838 (57/s) | **0.11%** (8) | — | 3,156 / 522 / 3,152 | pass: the dead instance is hidden |
| failover, bad balancer | 3,242 (27/s) | **27.5%** (891) | — | 1,080 / 190 / 1,081 | **fails**: a third of the traffic goes to the dead instance |

**How to read them:**
- **Stress:** the first component to saturate is the **gateway** (at its 0.5 CPU limit while the instances were at 15-50%). It is the single entry point, so it is also the first bottleneck. Adding instances does not help past that point; the gateway would need more CPU or its own replicas.
- **Failover:** with the good balancer, Retry sends the request to the next instance at once, and the health check removes the dead one within 5 s. With the bad balancer, round robin keeps sending one request in three to the dead instance. Those requests fail, and throughput halves because clients wait on failed connections.

|---|---|---|---|---|

## How to Run

**Requirements:** JDK 17, Maven and PostgreSQL. Node.js 18+ only if you want to run the tests.

1. Create the database in PostgreSQL:
   ```sql
   CREATE DATABASE "PrograWeb";
   ```
2. The connection is read from environment variables, with local defaults in `src/main/resources/application.properties`:

   | Variable | Default |
   |---|---|
   | `SPRING_DATASOURCE_URL` | `jdbc:postgresql://localhost:5432/PrograWeb` |
   | `SPRING_DATASOURCE_USERNAME` | `postgres` |
   | `SPRING_DATASOURCE_PASSWORD` | `1234` |

   If your local password is different, set the variable instead of editing the file:
   ```powershell
   $env:SPRING_DATASOURCE_PASSWORD="YOUR_PASSWORD"
   ```
3. Run the application:
   ```bash
   mvn spring-boot:run
   ```
4. Open in the browser:
   - Home and CRUD: http://localhost:8080
   - Page 1: http://localhost:8080/pagina1.html
   - Page 2: http://localhost:8080/pagina2.html

Tables are created automatically thanks to `spring.jpa.hibernate.ddl-auto=update`.

## Run with Docker

**Requirements:** Docker Desktop (no JDK, Maven or PostgreSQL needed).

```bash
docker compose up --build      # builds the images and starts gateway + app1 + app2 + app3 + PostgreSQL
docker compose down            # stops everything (add -v to also delete the data)
```

- App (through the API Gateway): http://localhost:8080. Instances directly: http://localhost:8081, :8082, :8083. The first start takes a few minutes: instances start one after another.
- Rick and Morty API through the gateway: http://localhost:8080/rickandmorty/character/?name=rick
- Gateway health: http://localhost:8080/actuator/health
- PostgreSQL (from the host): `localhost:5433`, database `PrograWeb`. Port 5433 avoids clashing with a local PostgreSQL.
- Credentials: copy `.env.example` to `.env` and change `DB_USERNAME` / `DB_PASSWORD` if needed. `.env` is ignored by git.

The published image can also be pulled directly:

```bash
docker pull ghcr.io/jeyby99/prograweb:latest
docker pull ghcr.io/jeyby99/prograweb-gateway:latest
```

| `ci.yml` | Push or PR to `dev`, `test`, `main` | Maven build (Java 17), Playwright e2e tests (in the official Playwright container) and a Docker image build without pushing |
| `docker-publish.yml` | Push to `main` (or manual run) | Builds and pushes `ghcr.io/jeyby99/prograweb` with tags `latest` and `sha-<commit>` |

On CI, Playwright retries a failed test up to 2 times because some tests depend on timing (debounce and chained requests). Locally there are no retries.

## Development Workflow

Every change follows the same path, from Jira to `main`:

```
Jira ticket (SCRUM-X) ──► feature/SCRUM-X-short-name ──PR──► dev ──PR──► test ──PR──► main ──► GHCR image
```

1. **Jira first.** Create a ticket in the `SCRUM` project with a clear description and acceptance criteria. Work belongs to the epic `SCRUM-6`.
2. **Branch.** Create `feature/SCRUM-X-short-name` from `dev`.
3. **Commits.** Every commit message starts with the ticket key, for example `SCRUM-8: Add docker-compose with PostgreSQL`.
4. **Pull requests.** Open a PR to `dev` with the Jira link, what changed, why, and how it was tested. CI must pass, and the PR gets a review comment before it is merged.
5. **Promotion.** `dev` → `test` (testing) → `main` (release) through PRs. Merging into `main` publishes the Docker image.
6. **Language.** All documentation, code comments, commits, PRs and Jira tickets are written in English.

| Branch | Purpose |
|---|---|
| `main` | Stable version; every update publishes the Docker image |
| `test` | Integration and testing before release |
| `dev` | Development; feature branches are merged here |
| `feature/SCRUM-X-*` | One branch per Jira ticket |
